CONTEXTO DO DOCUMENTO
--------------------------------------------------------------------------------
Análise técnica do frontend do e-commerce "Sunset Tabas" (repositório:
C:\Users\pablo\Documents\juite\frontend): arquitetura frontend↔backend
(Etapa 1), contrato de comunicação com o backend — rotas, RPCs, endpoints,
parâmetros, payloads (Etapa 2), o HTML obrigatório e a dinâmica obrigatória
de cada uma das 13 páginas de cliente (Etapa 3), os dois mecanismos com
reprodução exata de código — mapa de rastreio do motoboy em /consultar e
slot de resgate de cupom em /cliente/cupons (Anexos A e B), interações,
diálogos e máquinas de estado (Etapas 4-6), persistência de estado no
cliente (Etapa 7) e inventário de componentes de interface (Etapa 8).

A Etapa 3 descreve cada uma das 13 páginas de cliente em exatamente 2
listas:

  - "HTML obrigatórios": toda peça que compõe a tela, nomeada de forma
    simples e genérica (botão, imagem, texto, campo de texto, lista, ícone,
    card, checkbox, seletor) — NUNCA por classe CSS, cor, sombra, formato
    ou qualquer decisão visual. A lista é exaustiva: cada peça que existe
    na tela entra numa linha própria, uma abaixo da outra, sem agrupar
    várias peças numa frase só.
  - "Dinâmicas obrigatórias entre os HTML": toda regra de comportamento
    que liga essas peças entre si — o que aparece/some, o que cada clique
    dispara, em que ordem as coisas acontecem, que validação bloqueia o
    quê. Também uma explicação por linha, sem resumir várias dinâmicas
    numa frase só.

Um elemento só entra na lista de "HTML obrigatórios" se tiver função
própria (dispara ação, mostra dado, recebe entrada). Um `<div>`/`<span>`
puramente estrutural (wrapper de layout sem ação própria) não é listado.
Nenhuma das duas listas menciona cor, estilo, CSS, animação decorativa,
sombra, glow, gradiente ou formato (circular, flutuante, pílula etc.) — só
existência da peça e comportamento funcional dela.

Duas dinâmicas têm reprodução EXATA exigida (não é "qualquer gesto de
arrastar" ou "qualquer mapa") — o mapa de rastreio do motoboy (/consultar)
e o slot de arrastar-pra-resgatar (/cliente/cupons). O código-fonte real
desses dois mecanismos está reproduzido nos ANEXOS A e B, logo após a
Etapa 3 — a AÇÃO e a ANIMAÇÃO desses dois são obrigatórias tal como estão;
só a pele visual ao redor (cores, textura do "papel", ícones) é livre.

Stack técnica identificada:
- React 19 + TypeScript, Vite, React Router 7 (SPA client-side routing).
- Tailwind CSS v4 (classes utilitárias + poucas classes customizadas
  "sunset-*" que carregam o estilo visual específico do tema atual — essas
  são o que muda entre skins, nunca a lógica por trás delas).
- Zustand (+ middleware `persist`) para estado global no cliente.
- Framer Motion para animações de entrada/saída/transição.
- Leaflet (+ tiles CARTO) para os mapas de rastreio/seleção de endereço.
- Supabase (Postgres + RPC + RLS) como backend principal do fluxo público
  (catálogo, checkout, consulta, conta de cliente) — chamado DIRETO do
  browser via `@supabase/supabase-js`, sem passar pelo backend Rust.
- Backend Rust/Axum (Railway) só para: envio de WhatsApp (Evolution API) e
  notificações administrativas — o cliente final só toca esse backend em
  1 chamada (pedido de código de recuperação de senha) e em 1 chamada
  best-effort não bloqueante (aviso de "pedido criado").
- Vercel Edge Functions para o fluxo de pagamento Pix (criar cobrança,
  checar status, simular pagamento em ambiente de teste).

Escopo deste documento: as 13 páginas PÚBLICAS DE CLIENTE (rotas fora de
/admin e /funcionarios) e todo componente compartilhado que elas usam. As
áreas internas (/admin/*, /funcionarios/*) existem no mesmo repositório mas
são ferramentas de equipe (admin, vendedor, motoboy) — fora do escopo pedido
("páginas do cliente"), mencionadas aqui só onde a página de cliente depende
delas (ex.: dados que o admin configura e o cliente só lê).

1.1 — INVENTÁRIO DA CAMADA DE COMUNICAÇÃO (estado ATUAL, como está hoje)
--------------------------------------------------------------------------------

O projeto NÃO usa a nomenclatura clássica "services/providers/hooks/adapters/
controllers" como pastas separadas. A camada de comunicação está concentrada
em `src/lib/`, assim:

- src/lib/api.ts (ApiClient único)
  Exporta um único objeto `export const api = USE_LOCAL_DB ? localApi : remoteApi`.
  É o ÚNICO ponto que toda página/componente importa para falar com o
  backend (`import { api } from '../lib/api'`). `USE_LOCAL_DB` é decidido uma
  vez, no carregamento do módulo, a partir de variável de ambiente
  (`VITE_USE_LOCAL_DB`) ou de produção sem Supabase configurado — fallback
  automático para um "backend fake" 100% em localStorage
  (src/lib/localApi.ts + localData.ts), usado só para demonstração sem
  infraestrutura.
  `remoteApi` é o objeto composto que decide, por módulo, se a chamada vai:
    (a) direto pro Supabase (RPC/tabela) via src/lib/supabasePublicApi.ts —
        maioria do fluxo público de cliente;
    (b) pro backend Rust via `fetch(`${API_BASE}${path}`)` (função `request`
        interna de api.ts) — só 2 chamadas do lado cliente:
        `customerAuth.requestPasswordReset` e `orders.notifyCreated`;
    (c) pra uma Vercel Edge Function via `fetch(path)` relativo (função
        `callVercelPixApi` interna de api.ts) — as 3 chamadas de Pix
        (`orders.createPixPayment/refreshPayment/simulatePixPaid`).
  Do ponto de vista de QUEM CHAMA (a página), essa escolha é invisível —
  `api.orders.create(...)` sempre parece a mesma chamada, não importa o
  transporte por trás. Esse é o ÚNICO ponto de acoplamento consciente e
  intencional: as páginas dependem só da FORMA do objeto `api`, nunca de
  COMO cada chamada é transportada.

- src/lib/supabasePublicApi.ts (o "adapter" de fato do fluxo público)
  Objeto `supabasePublicApi` com um método por operação pública, cada um
  chamando `supabase.rpc(nome_da_funcao, {p_argumento: valor, ...})` ou
  `supabase.from(tabela).select(...)`. É aqui que mora o contrato exato
  (nome da RPC no Postgres + nome de cada parâmetro `p_*`) — ver 1.3.

- src/lib/apiError.ts
  Classe `ApiError extends Error { status: number }`. Todo erro de rede/RPC
  vira uma instância disso antes de chegar na página, que faz
  `e instanceof ApiError ? e.message : '<mensagem genérica>'`.

- src/lib/localApi.ts + src/lib/localData.ts ("modo demonstração")
  Reimplementação completa das mesmas operações usando só localStorage —
  espelha byte a byte o formato de retorno do Supabase, para a página nunca
  saber a diferença. Só ativa sem Supabase configurado.

- src/store/*.ts (Zustand — a camada de ESTADO GLOBAL / "providers")
  Cada arquivo é 1 store independente, todos com o padrão
  `create<State>()(persist((set) => ({...}), {name: 'chave_no_localStorage'}))`.
  Nenhuma store chama a API — elas só guardam o que a página escreve nelas
  depois de receber a resposta. Ou seja: STORE = ESTADO, PÁGINA = ORQUESTRAÇÃO,
  API = TRANSPORTE. Essa separação já existe e deve ser preservada.
  Stores relevantes ao cliente:
    * store/cart.ts        → useCart        (carrinho normal do catálogo)
    * store/cartDrawer.ts  → useCartDrawer  (abre/fecha o painel lateral da sacola)
    * store/bannerCart.ts  → useBannerCart  (carrinho separado, só da promoção /banner)
    * store/customer.ts    → useCustomer    (rascunho de dados de checkout)
    * store/customerAuth.ts→ useCustomerAuth(sessão de login do cliente)

- HOOKS: não existem custom hooks de dados (não há `useProducts()`,
  `useOrders()` etc.) — cada página faz sua própria chamada `useEffect` +
  `useState` + `api.x.y().then(setState)`. Isso é uma DUPLICAÇÃO DE LÓGICA
  real (ver 1.2).

- CONTEXTS (React Context API): não são usados em nenhum lugar do fluxo de
  cliente. Todo estado cross-componente passa por Zustand.

- CACHE: não existe camada de cache de requisição (nada tipo React Query/SWR).
  Toda tela que precisa de um dado o busca de novo ao montar. Único "cache"
  são as próprias stores persistidas (que guardam ESTADO DE USUÁRIO, não
  cache de resposta de servidor).

1.2 — ACOPLAMENTO DESNECESSÁRIO ENCONTRADO (documentado, não corrigido)
--------------------------------------------------------------------------------

a) Toda página importa `api` diretamente de `lib/api`. Não existe camada
   intermediária (service/hook) entre o componente visual e o cliente HTTP.
   Isso significa que TROCAR o layout de uma página hoje exige recriar
   também toda a lógica de fetch/estado dela — o "esqueleto funcional" e a
   "pele visual" estão no mesmo arquivo `.tsx`, entrelaçados.

b) Padrão idêntico repetido em 6+ páginas sem abstração:
   `useEffect(() => { api.X.list().then(setY).finally(() => setLoading(false)) }, [])`
   — ex.: Catalogo.tsx, Carrinho.tsx, FavoritosCliente.tsx, CuponsCliente.tsx,
   HistoricoCliente.tsx, Checkout.tsx, Banner.tsx, BannerCheckout.tsx todos
   reimplementam essa combinação loading/data/error manualmente.

c) O padrão de favoritar (fetch de lista de favoritos + toggle otimista +
   Set<string> local) está DUPLICADO, quase char-a-char, em 3 lugares
   diferentes: Catalogo.tsx, Carrinho.tsx e FavoritosCliente.tsx (esta
   última com pequena variação: aqui remover de fato tira o card da tela).

d) `ProductDetailModal` (o "toggle de detalhes do produto") é importado e
   orquestrado (estado `detailProduct`, handlers `onAdd/onRemove/onToggleFavorite`)
   de forma repetida em Catalogo.tsx, Carrinho.tsx e FavoritosCliente.tsx —
   o MESMO componente, a MESMA API de props, mas a lógica de "quem está
   favoritado"/"quanto tem no carrinho" é recalculada localmente em cada página.

e) O cálculo de desconto (cupom + promoção + produto-em-promoção-de-catálogo)
   dentro de Checkout.tsx é uma função de ~100 linhas inline, não extraída —
   replicada parcialmente (versão simplificada, só cupom) em BannerCheckout.tsx.

f) `lib/types.ts` é o único lugar com as interfaces de dados — isso já está
   bem centralizado (nenhuma duplicação de "shape" de Product/Order/etc.
   encontrada), é um ponto FORTE da arquitetura atual a ser preservado.

2.2 — Endpoints REST (backend Rust, Railway)
--------------------------------------------------------------------------------
  POST /api/customer/request-password-reset  body:{whatsapp}     → void
  POST /api/orders/notify-created             body:{order_id}    → void (best-effort, erro é ignorado no front)

2.3 — Endpoints (Vercel Edge Functions, mesmo domínio do front)
--------------------------------------------------------------------------------
  POST /api/pix-create   body:{order_id}  → Order (com pix_qr_base64/pix_copia_cola preenchidos)
  POST /api/pix-check    body:{order_id}  → Order (status atualizado)
  POST /api/pix-simulate body:{order_id}  → Order (marca como pago — só ambiente de teste)

2.4 — Botões/ações OBRIGATÓRIOS (o backend/negócio depende deles existirem)
--------------------------------------------------------------------------------
  - Um jeito de finalizar pedido (chama create_order) — obrigatório em
    /checkout e /banner/checkout.
  - Um jeito de aplicar cupom digitado (chama validate_coupon) — em /checkout
    e /banner/checkout (o segundo só se a promoção aceitar cupom).
  - Um jeito de consultar pedido por WhatsApp (track_orders_by_phone) — em
    /consultar, é a ÚNICA forma de um cliente NÃO LOGADO ver o status do
    próprio pedido.
  - Um jeito de logar/cadastrar (customer_login / customer_register) — pré-
    requisito de: finalizar checkout, ver favoritos, ver cupons, ver
    histórico, "Acompanhar entrega" a partir da Landing.
  - Um jeito de recuperar senha em 3 passos (pedir código → verificar
    código → trocar senha) — os 3 passos são RPCs/endpoints SEPARADOS,
    nenhum pode ser pulado.
  - Um jeito de resgatar o cupom pendente em 2 passos DISTINTOS: peek
    (não gasta) → claim (gasta) — nunca podem virar 1 passo só, ou o cliente
    perde a chance de "ver antes de confirmar".
  - Um jeito de copiar o código Pix (`navigator.clipboard.writeText`) e um
    jeito de simular pagamento (ambiente de teste) em /pagamento/:orderId.
  - Polling de pagamento em /pagamento/:orderId (refreshPayment a cada 4s
    enquanto não pago) — sem isso o cliente nunca vê a confirmação sem
    recarregar a página manualmente.
  - Polling de posição do motoboy em /consultar quando status =
    'em_rota_de_entrega' (a cada 5s) + polling de rota (a cada 25s).

2.5 — Parâmetros obrigatórios do formulário de checkout (ambos: /checkout e /banner/checkout)
--------------------------------------------------------------------------------
  customer_name (obrigatório, não vazio)
  customer_whatsapp (obrigatório, ≥10 dígitos, sempre normalizado com
    prefixo "55" antes de mandar pro backend)
  customer_birthdate (obrigatório — o backend/regra de negócio EXIGE maior
    de 18 anos; o front calcula a idade e bloqueia ANTES de chamar
    create_order, mas o valor em si sempre é enviado)
  delivery_type: 'entrega' | 'retirada' (nunca 'balcao' nesse fluxo — esse
    terceiro valor só existe pro PDV do admin/vendedor)
  Se 'entrega': neighborhood, address, customer_lat, customer_lng
    obrigatórios (vêm do LocationPicker)
  payment_method: 'pix' | 'cartao' | 'dinheiro'
  (Dinheiro no checkout/PDV/baixa: UX de valor recebido + Troco com máscara
  terminal BR em CashAmountInput — valor é validação de UI; não há coluna
  separada de cash_received no backend neste contrato.)
  items: array de {product_id, quantity} — nunca vazio
  coupon_code / promotion_id: opcionais

--- src/lib/geo/mapa.ts (tiles + ajuste de enquadramento) ---
```ts
export const TILE_URL = 'https://{s}.basemaps.cartocdn.com/rastertiles/dark_all/{z}/{x}/{y}{r}.png'
export const TILE_ATTR =
  '&copy; <a href="https://www.openstreetmap.org/copyright">OpenStreetMap</a> &copy; <a href="https://carto.com/attributions">CARTO</a>'

// Centro usado quando o cliente nega o GPS (coordenada física da loja).
export const FALLBACK = { lat: -7.1746, lng: -34.8576 }

// Avisa quando os tiles estão de fato falhando em carregar (rede/CDN),
// separado de "carregou mas está difícil de ver".
export function monitorarTiles(layer: L.TileLayer, onMudarStatus: (falhando: boolean) => void): () => void {
  let falhasSeguidas = 0
  const onErro = () => { falhasSeguidas++; if (falhasSeguidas >= 3) onMudarStatus(true) }
  const onCarregou = () => { falhasSeguidas = 0; onMudarStatus(false) }
  layer.on('tileerror', onErro)
  layer.on('tileload', onCarregou)
  return () => { layer.off('tileerror', onErro); layer.off('tileload', onCarregou) }
}

// Encaixa bounds (2 pontos) no espaço VISÍVEL de verdade — não usa o
// fitBounds nativo do Leaflet porque, com o mapa rotacionável (div
// oversized ~2.6x, ver ANEXO abaixo), ele calcula zoom errado. Mede o
// tamanho VISÍVEL real e calcula o zoom certo via projeção geográfica.
export function ajustarParaCaber(map: L.Map, bounds: L.LatLngBounds, visivel: { width: number; height: number }, paddingPx = 40) {
  const p1 = map.project(bounds.getNorthWest(), 0)
  const p2 = map.project(bounds.getSouthEast(), 0)
  const boundsW = Math.max(Math.abs(p2.x - p1.x), 1e-9)
  const boundsH = Math.max(Math.abs(p2.y - p1.y), 1e-9)
  const availW = Math.max(1, visivel.width - paddingPx * 2)
  const availH = Math.max(1, visivel.height - paddingPx * 2)
  const escala = Math.min(availW / boundsW, availH / boundsH)
  const zoom = Math.min(map.getMaxZoom(), Math.max(map.getMinZoom(), Math.log2(escala)))
  map.setView(bounds.getCenter(), zoom, { animate: false })
}
```

--- src/lib/geo/rotacaoMapa.ts (gesto unificado: arrastar+pinçar+girar) ---
Motivo de existir: o mapa gira via `transform: rotate()` numa div POR FORA
do controle do Leaflet; o dragging/touchZoom NATIVOS do Leaflet não sabem
disso e ficam "errados" assim que o mapa gira uma vez. A solução é
desligar os gestos nativos e reimplementar arrastar+pinçar+girar como 1
gesto só, sempre convertendo "quanto o dedo moveu na tela" pra "quanto o
mapa deve se mover de verdade", levando a rotação atual em conta.
```ts
export interface GestoMapaOpcoes {
  map: L.Map
  getRotation: () => number
  onRotate: (anguloGraus: number) => void
  enabled?: () => boolean
  onInteract?: () => void
}
interface PontoTela { x: number; y: number }
function centroide(a: PontoTela, b: PontoTela) { return { x: (a.x + b.x) / 2, y: (a.y + b.y) / 2 } }
function distancia(a: PontoTela, b: PontoTela) { return Math.hypot(a.x - b.x, a.y - b.y) }
function anguloEntre(a: PontoTela, b: PontoTela) { return (Math.atan2(b.y - a.y, b.x - a.x) * 180) / Math.PI }
function deTouch(t: Touch): PontoTela { return { x: t.clientX, y: t.clientY } }

// Roda um vetor de deslocamento de tela pelo inverso da rotação atual.
function rotacionarVetor(dx: number, dy: number, anguloGraus: number): [number, number] {
  const rad = (-anguloGraus * Math.PI) / 180
  const cos = Math.cos(rad), sin = Math.sin(rad)
  return [dx * cos - dy * sin, dx * sin + dy * cos]
}

export function anexarGestoMapa(el: HTMLElement, opcoes: GestoMapaOpcoes): () => void {
  const { map, getRotation, onRotate } = opcoes
  const enabled = opcoes.enabled ?? (() => true)
  const onInteract = opcoes.onInteract ?? (() => {})

  // touchmove dispara mais rápido do que o navegador pinta frames — só
  // ATUALIZA estado no evento (barato); um requestAnimationFrame por
  // frame real aplica o delta acumulado (evita o mapa "piscar" durante o
  // pinça, causado por chamar map.setZoom() várias vezes por frame).
  let ultimoMeioAplicado: PontoTela | null = null
  let ultimaDistanciaAplicada: number | null = null
  let ultimoAnguloAplicado: number | null = null
  let touchAtual: { pontos: PontoTela[] } | null = null
  let rafPendente = false

  function pan(dxTela: number, dyTela: number) {
    const [dx, dy] = rotacionarVetor(dxTela, dyTela, getRotation())
    map.panBy([-dx, -dy], { animate: false })
  }
  function agendarFlush() {
    if (rafPendente) return
    rafPendente = true
    requestAnimationFrame(() => { rafPendente = false; flush() })
  }
  function flush() {
    if (!touchAtual) return
    const { pontos } = touchAtual
    if (pontos.length === 1) {
      const p = pontos[0]
      if (ultimoMeioAplicado) pan(p.x - ultimoMeioAplicado.x, p.y - ultimoMeioAplicado.y)
      ultimoMeioAplicado = p; ultimaDistanciaAplicada = null; ultimoAnguloAplicado = null
      return
    }
    if (pontos.length === 2) {
      const [p0, p1] = pontos
      const meio = centroide(p0, p1), dist = distancia(p0, p1), ang = anguloEntre(p0, p1)
      if (ultimoMeioAplicado) pan(meio.x - ultimoMeioAplicado.x, meio.y - ultimoMeioAplicado.y)
      if (ultimaDistanciaAplicada != null && ultimaDistanciaAplicada > 0) {
        const fator = dist / ultimaDistanciaAplicada
        if (Number.isFinite(fator) && fator > 0) map.setZoom(map.getZoom() + Math.log2(fator), { animate: false })
      }
      if (ultimoAnguloAplicado != null) {
        let delta = ang - ultimoAnguloAplicado
        if (delta > 180) delta -= 360
        if (delta < -180) delta += 360
        onRotate(normalizarAngulo(getRotation() + delta))
      }
      ultimoMeioAplicado = meio; ultimaDistanciaAplicada = dist; ultimoAnguloAplicado = ang
    }
  }
  function onTouchStart(e: TouchEvent) {
    if (!enabled()) return
    if (e.touches.length === 1) {
      ultimoMeioAplicado = deTouch(e.touches[0]); ultimaDistanciaAplicada = null; ultimoAnguloAplicado = null
    } else if (e.touches.length === 2) {
      const p0 = deTouch(e.touches[0]), p1 = deTouch(e.touches[1])
      ultimoMeioAplicado = centroide(p0, p1); ultimaDistanciaAplicada = distancia(p0, p1); ultimoAnguloAplicado = anguloEntre(p0, p1)
    } else {
      ultimoMeioAplicado = null; ultimaDistanciaAplicada = null; ultimoAnguloAplicado = null
    }
    touchAtual = null
  }
  function onTouchMove(e: TouchEvent) {
    if (!enabled()) return
    if (e.touches.length !== 1 && e.touches.length !== 2) return
    e.preventDefault(); onInteract()
    touchAtual = { pontos: Array.from(e.touches).slice(0, 2).map(deTouch) }
    agendarFlush()
  }
  function onTouchEnd(e: TouchEvent) {
    touchAtual = null
    if (e.touches.length === 0) { ultimoMeioAplicado = null; ultimaDistanciaAplicada = null; ultimoAnguloAplicado = null }
    else if (e.touches.length === 1) { ultimoMeioAplicado = deTouch(e.touches[0]); ultimaDistanciaAplicada = null; ultimoAnguloAplicado = null }
  }
  // Mouse (desktop): arrastar com botão pressionado + roda pra zoom (sem girar — não existe "2 dedos" no mouse).
  let arrastandoComMouse = false
  let ultimoMouse: PontoTela | null = null
  function onMouseDown(e: MouseEvent) { if (!enabled() || e.button !== 0) return; arrastandoComMouse = true; ultimoMouse = { x: e.clientX, y: e.clientY } }
  function onMouseMove(e: MouseEvent) {
    if (!enabled() || !arrastandoComMouse || !ultimoMouse) return
    const p = { x: e.clientX, y: e.clientY }
    pan(p.x - ultimoMouse.x, p.y - ultimoMouse.y); ultimoMouse = p; onInteract()
  }
  function onMouseUp() { arrastandoComMouse = false; ultimoMouse = null }
  let deltaWheelPendente = 0
  function onWheel(e: WheelEvent) {
    if (!enabled()) return
    e.preventDefault(); onInteract()
    deltaWheelPendente += -Math.sign(e.deltaY) * 0.5
    if (rafPendente) return
    rafPendente = true
    requestAnimationFrame(() => {
      rafPendente = false
      if (deltaWheelPendente !== 0) { map.setZoom(map.getZoom() + deltaWheelPendente, { animate: false }); deltaWheelPendente = 0 }
      flush()
    })
  }
  el.addEventListener('touchstart', onTouchStart, { passive: true })
  el.addEventListener('touchmove', onTouchMove, { passive: false })
  el.addEventListener('touchend', onTouchEnd, { passive: true })
  el.addEventListener('touchcancel', onTouchEnd, { passive: true })
  el.addEventListener('mousedown', onMouseDown)
  window.addEventListener('mousemove', onMouseMove)
  window.addEventListener('mouseup', onMouseUp)
  el.addEventListener('wheel', onWheel, { passive: false })
  return () => {
    el.removeEventListener('touchstart', onTouchStart)
    el.removeEventListener('touchmove', onTouchMove)
    el.removeEventListener('touchend', onTouchEnd)
    el.removeEventListener('touchcancel', onTouchEnd)
    el.removeEventListener('mousedown', onMouseDown)
    window.removeEventListener('mousemove', onMouseMove)
    window.removeEventListener('mouseup', onMouseUp)
    el.removeEventListener('wheel', onWheel)
  }
}
export function normalizarAngulo(deg: number): number {
  let d = deg % 360
  if (d > 180) d -= 360
  if (d < -180) d += 360
  return d
}
```

A metáfora visual ("papel saindo de um corte na parede") é livre — pode

O que é OBRIGATÓRIO e não pode mudar: a máquina de estados do arrasto

quando parado (times e curva de easing abaixo).

--- Componente (src/components/coupon/CouponSlot.tsx) ---
```tsx
const SIZE = {
  sm: { width: 110, paperHeight: 190, rest: 50 },  // card decorativo (Landing), sem onReveal — só o loop
  lg: { width: 190, paperHeight: 220, rest: 70 },  // botão "Resgatar cupom" de verdade, arrastável
}

export default function CouponSlot({ header, bodyLines, footerLabel, footerValue, onReveal, disabled, size = 'lg', ariaLabel }: {
  header: ReactNode; bodyLines: ReactNode[]; footerLabel: string; footerValue: string
  onReveal?: () => void; disabled?: boolean; size?: 'sm' | 'lg'; ariaLabel?: string
}) {
  const preset = SIZE[size]
  const restY = -(preset.paperHeight - preset.rest)
  const interactive = !!onReveal

  const [dragY, setDragY] = useState<number | null>(null)
  const [snapping, setSnapping] = useState(false)
  const dragStartClientY = useRef<number | null>(null)
  const triggered = useRef(false)

  const onPointerDown = (e: React.PointerEvent<HTMLButtonElement>) => {
    if (!interactive || disabled) return
    dragStartClientY.current = e.clientY
    triggered.current = false
    setSnapping(false)
    setDragY(restY)
    e.currentTarget.setPointerCapture(e.pointerId)
  }
  const onPointerMove = (e: React.PointerEvent<HTMLButtonElement>) => {
    if (dragStartClientY.current == null) return
    const delta = e.clientY - dragStartClientY.current
    setDragY(Math.min(0, Math.max(restY, restY + delta)))
  }
  const onPointerUp = () => {
    if (dragStartClientY.current == null) return
    dragStartClientY.current = null
    const finalY = dragY ?? restY
    const progress = (finalY - restY) / (0 - restY)
    // ≥85% do curso puxado conta como "resgatado" — não precisa soltar
    // exatamente no zero.
    if (progress >= 0.85 && !triggered.current) {
      triggered.current = true
      setDragY(0)
      onReveal?.()
    } else {
      setSnapping(true)
      setDragY(restY)
    }
  }

  // Enquanto arrastando: segue o dedo 1:1, SEM transição (tempo real).
  // Soltando sem completar: 1 transição CSS de snap-back (0.3s ease).
  // Sem interação nenhuma: dragY fica null e a animação de loop (CSS,
  // ver abaixo) assume o controle.
  const secStyle = dragY != null
    ? { transform: `translateY(${dragY}px)`, transition: snapping ? 'transform 0.3s ease' : 'none', animation: 'none' }
    : undefined

  return (
    <div className="cs-wrapper">
      <div className="cs-cutout" />{/* "corte na parede" -- livre pra reskin */}
      <div
        className={`cs-sec ${size === 'sm' ? 'cs-sec-sm' : ''}`}
        style={secStyle}
        onTransitionEnd={() => { if (snapping) { setSnapping(false); setDragY(null) } }}
      >
        <button
          type="button" className="cs-paper" disabled={disabled} aria-label={ariaLabel}
          tabIndex={interactive ? 0 : -1} aria-hidden={!interactive}
          onPointerDown={onPointerDown} onPointerMove={onPointerMove} onPointerUp={onPointerUp} onPointerCancel={onPointerUp}
          style={{ pointerEvents: interactive ? 'all' : 'none', cursor: interactive ? 'grab' : 'default', touchAction: interactive ? 'none' : undefined }}
        >
          <TicketCardVisual header={header} bodyLines={bodyLines} footerLabel={footerLabel} footerValue={footerValue} />
        </button>
      </div>
    </div>
  )
}
```

  SE não favoritado → favorita na hora (sem confirmação) → ícone muda →
    chamada ao backend em paralelo (não bloqueia a UI).
  SE já favoritado → NÃO desfavorita direto → abre ConfirmRemoveDialog →
    "Remover" desfavorita de verdade (ícone muda, card PERMANECE na tela
    no Catálogo/Carrinho — só em Favoritos o card some) → "Cancelar" fecha
    sem alterar nada.

4.3 — Adicionar/ajustar quantidade direto no card (sem abrir modal)
--------------------------------------------------------------------------------
  Card sem item no carrinho → botão "Adicionar" → vira controle +/- na
    hora (sem reload/nova busca — é tudo estado local do Zustand `cart`).
  Card com item no carrinho → "-" decrementa (remove o controle e volta a
    "Adicionar" ao chegar em 0) → "+" incrementa até o limite de estoque
    (fica desabilitado no limite, nunca esconde o botão).

4.4 — Busca do Catálogo
--------------------------------------------------------------------------------
  Campo de busca
    ↓ foco
  Painel de sugestão aparece (vazio se o campo estiver vazio)
    ↓ digitação (sem debounce — filtra a cada tecla sobre a lista já
      carregada em memória, nunca busca no servidor de novo)
  Lista filtrada (até 8 resultados) aparece no painel, ou mensagem de
    "nenhum encontrado"/"digite pelo menos 3 letras" conforme o tamanho do
    texto.
    ↓ clique em um resultado
  Navega pra /produto/:id, campo e painel são limpos/fechados.
    ↓ clique fora do campo/painel (listener global de mousedown)
  Painel fecha sem limpar o texto digitado.
    ↓ clique no X dentro do campo
  Limpa o texto e tira o foco do campo.

4.5 — Filtro por categoria/aba de promoção
--------------------------------------------------------------------------------
  Aba "Todos" (padrão) → mostra tudo.
  Aba de categoria → filtra só aquela categoria.
  Aba "Promoção" (só existe se houver ≥1 produto em promoção) → filtra só
    produtos com desconto ativo, reagrupados visualmente por categoria
    original dentro da mesma tela.
  Categoria com produto em promoção ganha um sinal na própria aba, mesmo
    fora da aba "Promoção" (sinalização cruzada).

4.6 — Ordenação e alternância de visualização
--------------------------------------------------------------------------------
  Select de ordenação → recalcula a lista exibida instantaneamente (client-
    side, sobre os dados já carregados) — não dispara nova chamada de rede.
  Botões grade/lista → troca só o layout de exibição, mesmos dados,
    persistência é local ao componente (perde a escolha ao sair da página).

4.7 — Carrossel da Landing (banner/promoção) e abertura de /banner
--------------------------------------------------------------------------------
  Carrossel (1 card OU trilho, conforme configuração do admin)
    ↓ automático: avança sozinho a cada 3s (modo cards) ou 4.5s (modo atual)
      — LOOP CONTÍNUO, nunca fica parado num item só quando há 2+ itens,
      voltando pro primeiro item depois do último (looping infinito).
    ↓ manual: arrastar (pointer down→move→up) horizontal ≥40px conta como
      swipe (avança/recua conforme direção), cancela o clique que viria
      em seguida
    ↓ toque curto sem arrastar (< 40px) conta como clique normal
  Clique no card ativo → navega pra /banner?promocao=:id (só se aquele
    item tiver uma promoção de verdade atrás — o "hero" estático sem
    promoção nenhuma cadastrada não é clicável). A página /banner então
    busca essa promoção pelo identificador recebido na URL e monta a
    vitrine dela (ver Etapa 3, seção /banner, e Etapa 3, seção /banner
    para as dinâmicas completas de tipo "kit" vs. "monte seu carrinho").

4.8 — Slot de resgate de cupom (o mais elaborado do sistema — ver ANEXO B
para a reprodução exata da máquina de estados e das animações)
--------------------------------------------------------------------------------
  Slot "CUPOM" (só visível quando há algo pra resgatar)
    ↓ loop decorativo contínuo (papel "espiando" pra fora, parado, sem
      interação do usuário ainda)
    ↓ pointerdown no papel
  Papel passa a seguir o dedo/mouse 1:1 (sem easing, tempo real)
    ↓ pointerup
  SE arrastou ≥85% do curso total → trava em 100% (fora do buraco) →
    dispara `onReveal` → abre overlay de tela cheia → chama peek (não
    gasta) → mostra o ticket → espera 2s → mostra botão "Resgatar cupom".
    ↓ clique em "Resgatar cupom"
  Chama claim (GASTA a concessão, de verdade, sem volta) → cupom entra na
    lista "Ativos" → overlay fecha → aba muda pra "Ativos" automaticamente
    → reverifica se sobrou mais algum cupom pendente (slot pode reaparecer).
  SE arrastou <85% do curso → papel volta deslizando suavemente (CSS
    transition) pro estado inicial → loop decorativo retoma → NADA é
    gasto, NADA foi chamado no backend (peek só dispara ao completar).

4.9 — Carrossel de tickets (abas Ativos/Inativos/Histórico)
--------------------------------------------------------------------------------
  Trilho horizontal com scroll-snap
    ↓ scroll (arrastar ou tocar em qualquer parte do trilho)
  A cada frame de scroll (throttled via requestAnimationFrame), recalcula
    qual card está mais perto do centro visual → esse card ganha escala
    maior + opacidade cheia + animação própria; os demais encolhem/apagam
    parcialmente e ficam parados (não animam, por performance).
  Trocar de aba reresolve o card ativo de novo (efeito reagindo a
    `[tab, data]`).

4.10 — Seletor de localização (LocationPicker)
--------------------------------------------------------------------------------
  Botão "Escolher localização no mapa" (Checkout/BannerCheckout)
    ↓ clique
  Abre tela cheia (portal direto pro <body>), passo "busca":
    ↓ digitar ≥3 caracteres (debounce 500ms) → lista de resultados de
      geocodificação
    ↓ OU clique em "Usar minha localização atual" → pede GPS do navegador
    ↓ clique num resultado (ou sucesso do GPS)
  Avança pro passo "ajuste": mapa em tela cheia com pino FIXO no centro da
    tela — é o MAPA que se move por baixo dele ao arrastar (padrão
    Uber/99).
    ↓ arrastar o mapa (`moveend`)
  Após soltar + debounce de 400ms: busca endereço reverso do novo centro +
    recalcula estimativa de frete em paralelo.
    ↓ SE fora do raio de entrega (`within_range === false`)
  Mostra aviso, mas ainda permite editar/tentar outro ponto — só bloqueia
    a CONFIRMAÇÃO final, não o ajuste do pino.
    ↓ clique em "Confirmar localização"
  SE fora do raio → mostra erro, não fecha. SE dentro do raio → devolve
    {lat, lng, label, bairro, estimate} pro componente pai (Checkout),
    fecha o seletor.
  Alternativa: digitar diretamente no campo de endereço da própria tela de
    ajuste também busca e move o pino pro resultado escolhido, sem
    precisar voltar pro passo de busca.

4.11 — Formulário de checkout: detecção automática de cupom
--------------------------------------------------------------------------------
  Campo de WhatsApp (Checkout)
    ↓ digitar até completar ≥10 dígitos
  Após 500ms de pausa (debounce): busca cupons exclusivos daquele número
    → SE encontrar, preenche automaticamente o PRIMEIRO como sugestão
      (`autoCoupon`) — mas isso é só o CAMPO ficando pronto pra seleção,
      não aplica nada sozinho.
    ↓ cliente digita/seleciona algo ativamente
  Só aí o cupom é de fato validado e aplicado (chamada de validate_coupon).

4.12 — Produto em promoção entrando/saindo do carrinho (Checkout)
--------------------------------------------------------------------------------
  Adicionar ao carrinho um produto que tem `coupon_code` de promoção
  atrelado (fora da tela de Checkout, em qualquer catálogo/card)
    ↓ ao chegar no Checkout, efeito detecta a correspondência
  SE não há outro cupom já aplicado → valida e aplica esse cupom
    AUTOMATICAMENTE (única auto-aplicação real do sistema, mas restrita a
    esse caso específico de produto-com-cupom-de-catálogo).
  Remover esse produto do carrinho → efeito detecta que o item que trouxe
    o desconto não está mais na lista → remove o cupom automático junto.

ETAPA 5 — TODAS AS CAIXAS DE DIÁLOGO (Dialogs/Modals)

5.1 — ProductDetailModal ("toggle de detalhes do produto")
--------------------------------------------------------------------------------
  Quando abre: clique em qualquer card de produto (Catálogo, Carrinho,
    Favoritos, sem promoção; NÃO usado no Banner, que tem seu próprio
    modal informativo mais simples).
  Quem abre: a própria página (estado `detailProduct`).
  Quem fecha: clique no X, clique fora do card (`onClick` no overlay),
    OU indiretamente ao confirmar remoção de favorito (só em Favoritos).
  Estados que possui: com/sem promoção aplicada, com/sem favorito
    (condicional a login), esgotado/disponível, com/sem item já no carrinho.
  Dados que manipula: 1 Product + 1 PromotionalProduct opcional + contagem
    no carrinho + flag de favorito.
  Ações que executa: favoritar/desfavoritar (delegado ao pai via
    `onToggleFavorite`), adicionar/remover do carrinho (delegado via
    `onAdd`/`onRemove`), fechar (`onClose`).
  Chamadas ao backend: NENHUMA diretamente — todas as chamadas reais
    (toggle de favorito) acontecem na página que o renderiza, o modal só
    dispara callbacks.
  Componentes que contém: imagem, botão de favoritar (com rótulo),
    nome, categoria, descrição, preço (com ou sem desconto riscado),
    controle de +/- ou botão adicionar, badge de desconto (se promoção).
  Confirmações que exige: NENHUMA diretamente — a confirmação de
    desfavoritar é responsabilidade da página (abre um SEGUNDO dialog,
    ConfirmRemoveDialog, por cima).
  Estrutura obrigatória (conforme pedido no prompt-base): imagem, título,
    descrição, preço, quantidade/controle, botão comprar, botão favorito,
    botão fechar. (Não existe botão de compartilhar nesta versão.)

5.2 — ConfirmRemoveDialog (confirmação genérica de ação destrutiva)
--------------------------------------------------------------------------------
  Quando abre: SEMPRE que o cliente tenta desfavoritar algo já favoritado
    (Catálogo, Carrinho, Favoritos) — hoje é o único uso real no fluxo de
    cliente, mas o componente é genérico o bastante pra qualquer ação
    destrutiva futura.
  Quem abre: a página, ao detectar clique de desfavoritar em item já
    favoritado (nunca ao favoritar pela primeira vez).
  Quem fecha: botão "Cancelar" (não faz nada) ou botão de ação (label
    customizável, default "Remover" — dispara `onConfirm`).
  Estados que possui: nenhum estado interno — é 100% controlado pelo pai
    (título/mensagem/labels vêm todos por prop).
  Dados que manipula: nenhum diretamente — só repassa a decisão do
    usuário pra cima via callback.
  Ações que executa: `onConfirm` (delegado) ou `onCancel` (delegado).
  Chamadas ao backend: nenhuma direta.
  Componentes que contém: ícone de alerta circular, título, mensagem,
    botão de ação (estilo "perigo"), botão cancelar.
  Confirmações que exige: é EM SI a camada de confirmação — não abre
    nada por cima dela.

5.3 — CustomerAuthModal (login / criar conta)
--------------------------------------------------------------------------------
  Quando abre: clique em "Acompanhar entrega" sem login (Landing),
    "Finalizar pedido" sem login (Checkout/BannerCheckout indireto via
    handleFinalizeClick), clique em "Entrar"/"Criar conta" no menu de
    convidado (BrandHeader, SiteHeader).
  Quem abre: qualquer página/componente que precise de sessão pra
    prosseguir uma ação.
  Quem fecha: X no canto, clique fora do card, OU sucesso de
    login/cadastro (`onSuccess`, que tipicamente também dispara a ação
    original que exigia login — ex.: Checkout tenta finalizar de novo
    sozinho após o modal fechar com sucesso).
  Estados que possui: modo (login|register), loading, error, e todos os
    campos de cada formulário (whatsapp/senha no login; nome/whatsapp/
    email/nascimento/senha no cadastro).
  Dados que manipula: sessão do cliente (token + Customer) — grava direto
    na store `useCustomerAuth` em caso de sucesso.
  Ações que executa: `api.customerAuth.login` ou `api.customerAuth.register`.
  Chamadas ao backend: as 2 acima.
  Componentes que contém: logo, alternância de abas login/cadastro,
    campos do formulário ativo, link "Esqueci minha senha" (só no modo
    login, navega pra /recuperar-senha E fecha o modal), botão de ação
    principal.
  Confirmações que exige: nenhuma — sucesso já é a confirmação implícita.
  Detalhe de UX obrigatório: campo "Criar conta" já vem PRÉ-PREENCHIDO
    com nome/whatsapp/nascimento se já existirem no rascunho de checkout
    (`store/customer`) — poupa redigitar o que já foi escrito ali (email
    nunca vem de lá, checkout não pede email).

5.4 — Modal de informação do produto (Banner, `infoProduct`)
--------------------------------------------------------------------------------
  Quando abre: clique na foto/botão de info de um produto dentro de /banner.
  Quem abre: a própria página Banner.
  Quem fecha: clique no X, ou clique fora do card (overlay).
  Estados que possui: nenhum próprio — controlado 100% pelo estado
    `infoProduct` do pai.
  Dados que manipula: nenhum — é só leitura/exibição.
  Ações que executa: nenhuma além de fechar.
  Chamadas ao backend: nenhuma.
  Componentes que contém: título, botão fechar, imagem (se existir),
    descrição (se existir), linha de preço.
  Confirmações que exige: nenhuma. É deliberadamente mais simples que o
    ProductDetailModal — não tem favoritar nem adicionar ao carrinho (a
    seleção de produtos do banner já acontece direto nos controles da
    lista, fora do modal).

5.5 — Overlay de revelação de cupom (tela cheia, dentro de CuponsCliente)
--------------------------------------------------------------------------------
  Quando abre: ao completar o gesto de arrastar o CouponSlot (≥85% do curso).
  Quem abre: a própria página CuponsCliente (`revealStage !== 'idle'`).
  Quem fecha: automaticamente ao concluir o resgate com sucesso
    (`revealStage` volta a 'idle') — NÃO tem botão de fechar/cancelar
    manual enquanto está revelando ou confirmando (é um fluxo guiado,
    proposital).
  Estados que possui: 'pulling' (buscando peek) → 'revealed' (mostrando +
    botão de confirmar, após 2s) → 'claiming' (confirmando).
  Dados que manipula: 1 ClaimedCoupon (preview, depois vira ativo de
    verdade).
  Ações que executa: peek (ao entrar em 'pulling'), claim (ao clicar
    confirmar em 'revealed').
  Chamadas ao backend: as 2 acima.
  Componentes que contém: spinner (enquanto sem preview), o ticket em si
    (CouponTicket, com animação de entrada tipo mola/spring), botão de
    confirmar (só no estado 'revealed'), texto "Resgatando…" (estado
    'claiming'), mensagem de erro (se peek ou claim falharem).
  Confirmações que exige: o botão "Resgatar cupom" acumulado ao gesto de
    arrastar JÁ É a confirmação em duas camadas (gesto físico + clique
    consciente) — não há um terceiro diálogo por cima.

ETAPA 6 — MÁQUINA DE ESTADOS DOS COMPONENTES INTERATIVOS

6.1 — Botão "Adicionar ao carrinho" / controle de quantidade (em qualquer card)
--------------------------------------------------------------------------------
  [Sem item no carrinho] --clique "Adicionar"--> [Com 1 item, mostra +/-]
  [Com N item(ns)] --clique "-"--> [Com N-1] (N-1=0 volta pro estado
    "Sem item no carrinho")
  [Com N item(ns)] --clique "+", N<estoque--> [Com N+1]
  [Com N item(ns), N=estoque] --"+"desabilitado--> (sem transição, botão
    inerte)
  [Qualquer estado] --produto sem estoque (quantity<=0)--> [Esgotado]
    (estado permanente pra aquele produto até voltar a ter estoque —
    substitui TODOS os controles acima por um rótulo fixo, sem interação)

6.2 — Coração de favorito (FavoriteHeartButton)
--------------------------------------------------------------------------------
  [Não favoritado] --clique--> [Favoritado] (direto, sem confirmação;
    chamada ao backend disparada em paralelo, não bloqueia a transição
    visual)
  [Favoritado] --clique--> [Aguardando confirmação] (abre
    ConfirmRemoveDialog, ícone NÃO muda ainda)
  [Aguardando confirmação] --"Cancelar"--> [Favoritado] (sem mudança)
  [Aguardando confirmação] --"Remover"--> [Não favoritado] (Catálogo/
    Carrinho) OU [Card removido da lista] (só em /cliente/favoritos)
  (Estado inicial "Não visível" quando sem sessão — o coração só existe
   no DOM quando `customerAuth.token` existe; sem token, este componente
   inteiro não é renderizado nos cards de Catálogo/Carrinho.)

6.3 — CouponSlot (arrasto de resgate — ver ANEXO B para o código exato)
--------------------------------------------------------------------------------
  [Idle, loop decorativo] --pointerdown--> [Arrastando, segue o dedo]
  [Arrastando] --pointerup, progresso<85%--> [Retornando (snap)] --fim da
    transição CSS--> [Idle, loop decorativo]
  [Arrastando] --pointerup, progresso>=85%--> [Travado em 100%] -->
    dispara onReveal --> (controle passa pro pai: revealStage)
  [Idle] --disabled=true (revealStage já não é 'idle')--> [Bloqueado pra
    novo toque] (evita disparar 2 resgates simultâneos)

6.4 — revealStage (CuponsCliente, estado do resgate como um todo)
--------------------------------------------------------------------------------
  'idle' --gesto completo do slot--> 'pulling'
  'pulling' --peek sucesso (+ 2s de espera fixa)--> 'revealed'
  'pulling' --peek falha--> 'idle' (com revealError preenchido)
  'revealed' --clique "Resgatar cupom"--> 'claiming'
  'claiming' --claim sucesso--> 'idle' (cupom já está na lista "Ativos",
    aba muda automaticamente, hasClaimable reverificado)
  'claiming' --claim falha--> 'revealed' (com revealError preenchido,
    permite tentar de novo sem refazer o gesto de arrastar)

6.5 — Botão "Finalizar pedido" (Checkout / BannerCheckout)
--------------------------------------------------------------------------------
  [Idle] --clique, sem sessão--> [Idle] (modal de login abre por cima,
    botão não muda de estado)
  [Idle] --clique, com sessão, loja FECHADA--> [Idle] (mensagem de loja
    fechada; NÃO chama orderService.create / create_order — cliente pode
    usar o resto do site, só não finaliza checkout)
  [Idle] --clique, com sessão, validação client-side falha--> [Idle] (com
    mensagem de erro específica, nenhuma chamada de rede disparada)
  [Idle] --clique, validação passa e loja aberta--> [Enviando] (botão
    desabilitado + spinner)
  [Enviando] --sucesso--> navega pra outra rota (pagamento ou consulta) —
    o componente é desmontado, não há "estado de sucesso" visual nesta
    própria tela.
  [Enviando] --falha--> [Idle] (com mensagem de erro, botão reabilitado)

6.6 — Botão "Copiar código Pix" (Pagamento)
--------------------------------------------------------------------------------
  [Idle, mostra ícone de copiar + "Copiar código Pix"] --clique--> [Copiado,
    mostra ícone de check + "Copiado!"] --após 2000ms (timeout)--> [Idle]

6.7 — Página Pagamento como um todo
--------------------------------------------------------------------------------
  [Carregando] --pedido encontrado, Pix sem cobrança ainda--> [Gerando
    cobrança] --sucesso ou falha (ambos avançam)--> [Aguardando pagamento]
  [Carregando] --pedido encontrado, já com cobrança ou já pago-->
    [Aguardando pagamento] ou [Pago] direto
  [Aguardando pagamento] --poll a cada 4s, ainda não pago--> [Aguardando
    pagamento] (mesmo estado, só atualiza `order` por baixo)
  [Aguardando pagamento] --poll detecta `payment_status==='pago'` OU
    clique em "simular pagamento"--> [Pago] (estado final, polling para
    de rodar — o `useEffect` do intervalo tem `order.payment_status` na
    dependência e retorna cedo quando já está pago)

6.8 — Carrossel da Landing / do carrossel de tickets de cupons (activeIndex)
--------------------------------------------------------------------------------
  [Item ativo = i] --temporizador OU swipe pra frente--> [Item ativo =
    (i+1) % total] (loop, nunca "acaba")
  [Item ativo = i] --swipe pra trás--> [Item ativo = (i-1+total) % total]
  (No carrossel de cupons, a métrica de "ativo" não é por índice fixo mas
   por distância até o centro do scroll — recalculada continuamente, não
   é uma máquina de estados discreta como o carrossel da Landing.)


================================================================================
ETAPA 7 — PERSISTÊNCIA DOS ESTADOS (mapa completo, OBRIGATÓRIO)
================================================================================

7.1 — O que É persistente hoje (sobrevive a F5 e a fechar/reabrir a aba)
--------------------------------------------------------------------------------
  Mecanismo: Zustand + middleware `persist`, que grava em `localStorage`
  (chave = nome dado em cada store) a cada mudança de estado, e restaura
  automaticamente na inicialização da store.

  | Store              | Chave localStorage      | Conteúdo                          | Onde é usado |
  |---------------------|--------------------------|-----------------------------------|---------------|
  | useCart              | sonset_cart              | items: [{productId, quantity}]    | Catálogo, Carrinho, Checkout, Consultar(indireto via Histórico "comprar novamente"), ProdutoDetalhe |
  | useBannerCart         | sonset_banner_cart       | promotionId, items                | Banner, BannerCheckout |
  | useCustomer            | sonset_customer          | name, whatsapp, birthdate, neighborhood, address, referencePoint, lat, lng | Checkout, BannerCheckout, Consultar (autopreenche busca), CustomerAuthModal (autopreenche cadastro) |
  | useCustomerAuth (sessão)| sonset_customer_auth   | token, customer                   | TODAS as páginas de cliente (gate de login) |

7.2 — Comportamentos de persistência EXIGIDOS explicitamente (regras do produto)
--------------------------------------------------------------------------------
  ✔ Favoritar um produto DENTRO do ProductDetailModal e fechar o modal —
    o favorito NÃO se perde (já garantido hoje: o estado real vive na
    página que renderiza o modal + é persistido no backend a cada toggle;
    reabrir o modal do mesmo produto reflete o estado atual porque a
    própria lista de `favoriteIds` já foi atualizada).
  ✔ Fechar um modal (qualquer um) NUNCA desfaz uma ação já confirmada —
    confirmado hoje: nenhum dos modais tem "cancelar tudo ao fechar" —
    toda ação (favoritar, adicionar ao carrinho) já foi persistida no
    momento do clique, o fechamento do modal é puramente visual.
  ✔ Reabrir um modal reflete o estado ATUAL — garantido porque os modais
    são 100% controlados por props vindas do estado da página (nunca têm
    estado interno "esquecido" de uma abertura anterior).
  ✔ Trocar de página nunca apaga estado válido — garantido: `cart`,
    `bannerCart`, `customer` e `customerAuth` são todos Zustand persistido,
    sobrevivem a navegação entre rotas (são globais à SPA) e a fechar/
    reabrir a aba.
  ✔ Atualizar a página (F5) não apaga o que deveria permanecer —
    confirmado para os 4 stores acima. NÃO se aplica (nem deveria) a
    estado de UI local de cada página (filtros, aba selecionada, texto de
    busca, modal aberto) — isso é esperado resetar ao recarregar, e
    HOJE JÁ RESETA (comportamento correto, não é bug).
  ✔ Carrinho permanece → sim, `useCart` (`sonset_cart`).
  ✔ Favoritos permanecem → SIM, mas de forma DIFERENTE dos outros: favoritos
    NÃO são persistidos no cliente (não tem store Zustand própria) — a
    fonte de verdade é 100% o BACKEND (`customer_list_favorites`), buscada
    de novo a cada visita de Catálogo/Carrinho/Favoritos. Isso é
    CORRETO E INTENCIONAL (favorito é dado de conta de cliente, não
    rascunho de sessão de aba) — não confundir com um "bug de
    persistência": é persistência via backend, não via localStorage.
  ✔ Cupons aplicados permanecem "enquanto fizer sentido" → o cupom
    aplicado no Checkout é estado LOCAL da página (`appliedCoupon`), NÃO
    persistido — se o cliente sair do Checkout e voltar, precisa
    reaplicar. Isso é o comportamento ATUAL; se o requisito de produto for
    "deve sobreviver a navegação", seria necessário mover esse estado pra
    uma store persistida — DOCUMENTADO AQUI COMO LACUNA, não corrigido
    nesta análise.
  ✔ Preferências do usuário permanecem → o rascunho de checkout
    (`useCustomer`) cumpre esse papel pros dados de identificação/entrega.

7.3 — O que é TEMPORÁRIO (propositalmente, nunca deveria persistir)
--------------------------------------------------------------------------------
  - Todo filtro/busca/ordenação/aba selecionada em qualquer página (search,
    categoryFilter, sortBy, view, tab) — estado local via `useState`,
    reseta ao trocar de página ou recarregar. CORRETO.
  - Estado de abertura de QUALQUER modal/dialog/dropdown — sempre
    `useState` local, nunca deveria sobreviver a navegação.
  - `appliedCoupon`/`couponInput`/`autoCoupon` do Checkout — ver 7.2,
    marcado como lacuna, não bug.
  - `shippingEstimate` — recalculado a cada entrada na tela (Checkout já
    revalida na montagem se já havia lat/lng salvo, porque o preço por km
    pode ter mudado desde a última visita).
  - Estado de swipe/drag em qualquer carrossel/slot (posição durante o
    gesto) — sempre local, nunca persistido, reseta a cada novo gesto.

ETAPA 9 — CONTRATO TÉCNICO CONSOLIDADO (invariantes de rota, RPC e regra de negócio)
================================================================================

  - Nomes de RPC/endpoint (ver Etapa 2): create_order, validate_coupon,
    customer_claim_coupon, customer_peek_claimable_coupon, etc., e seus
    parâmetros `p_*`.
  - Shape dos payloads enviados/recebidos: campos de `lib/types.ts`.
  - Nomes das rotas: `/`, `/catalogo`, `/produto/:id`, `/carrinho`,
    `/checkout`, `/banner`, `/banner/checkout`, `/pagamento/:orderId`,
    `/consultar`, `/recuperar-senha`, `/cliente/favoritos`,
    `/cliente/cupons`, `/cliente/historico`.
  - Fluxo de telas: 3 passos de recuperação de senha (WhatsApp → código →
    nova senha), 2 passos peek→claim de resgate de cupom, 2 passos
    busca→ajuste do seletor de endereço, login exigido antes de finalizar
    pedido/ver favoritos/cupons/histórico.
  - Favoritos (contrato de autenticação): (1) Favoritar um item — somente
    cliente logado; se deslogado, abre login/criar conta e NÃO grava o
    favorito. (2) Acessar `/cliente/favoritos` — somente logado; se
    deslogado, redireciona ao login e NÃO vê a lista.
  - Sequência de ações dentro de cada fluxo: cupom de fidelidade nunca se
    auto-aplica sozinho (só o cupom de produto em promoção de catálogo se
    auto-aplica); carrinho de banner é sempre separado do carrinho normal;
    produto esgotado bloqueia compra em toda superfície onde aparece.
  - Comportamento de cada componente: estados possíveis, quando abre/fecha
    um modal, quando confirma vs. quando age direto (ver Etapas 5 e 6).
  - Os 4 stores de estado persistente: chaves de localStorage e shape dos
    dados (ver Etapa 7).
  - Regras de negócio: maioridade 18 anos no checkout, normalização de
    WhatsApp com prefixo 55, cálculo de desconto com 3 fontes possíveis
    (promoção de campanha, cupom, produto em promoção de catálogo)
    exibidas em linhas separadas no resumo, raio de entrega bloqueando a
    confirmação de endereço fora do alcance.
  - Reprodução exata (gesto + animação) do mapa de rastreio (ANEXO A) e do
    slot de resgate de cupom (ANEXO B).
  - Loja fechada: landing cinza + banner FECHADA/abre {próximo dia};
    checkout NÃO finaliza (create_order bloqueado no cliente).
  - Logo: upload em /meu-plano/layout → tenant-config.logo_url → header home.
  - Textos do hero: landing_headline / landing_sub / landing_badge via
    tenant-config, editáveis no CMS preview 1:1 de /meu-plano/layout.
  - CartFab: estilo sacola|#cart_icon (+ animate) via tenant-config;
    obrigatório nas páginas de cliente, canto inferior direito.
  - Hub lojista: rotas /meu-plano, /meu-plano/layout, /meu-plano/financeiro,
    /meu-plano/redes.
